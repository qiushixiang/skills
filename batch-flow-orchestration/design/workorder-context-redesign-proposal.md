# 工单模型与信息传递整改方案（已实施并独立审阅）

日期：2026-11-08。修订：补充负责人选材、必读编制与重点约束保留要求。用户已批准本方案；实施与验证结果另行记录，本文不代表测试或任务已完成。

## 1. 对工单模型的判断

工单用于表达一次明确工作、分配角色、保留结果及恢复进度，这个方向成立；当前实现没有建立可靠的“当前有效执行要求”，不应仅凭已有测试通过就认为整个模型已经合理。

保留三个具有不同职责的对象：

| 对象 | 唯一职责 | 不应承担的职责 |
|---|---|---|
| 计划 | 用户批准的交付目标、验收、依赖、角色和预算配置 | 反复累加历史恢复说明、复制每轮工作指令 |
| 工单 | 针对一个目标的本次工作、角色、有效约束、所需输入和当前执行状态 | 充当全部项目历史的汇总文档 |
| 运行记录 | 某次调用实际收到的输入、使用的版本、原始输出和事实证据 | 被直接重放为后续工单的有效命令 |

卡片、dispatch.json 都是工单的派发导出物，用于复现当时实际送达内容；不是可独立维护的新任务来源。目标和验收由唯一计划来源生成到当前工单正文，使实施者直接知道要完成什么；不维护第二份可独立修改的缓存，也不只甩给实施者一个计划引用让其自行寻找任务定义。

不新增工单类型、调度平台、通用上下文图引擎、语义冲突规则引擎或额外审批节点。保留现有角色及审阅流程，重做信息组织和派发链路。

## 2. 已核实的失效路径

- S17 原首轮卡片同时出现全局 execution_notes 中的“S17～S20 原暂停保留”和结构化状态中的 S17 已解锁。后续将新决定继续追加到同一说明末尾，没有移除旧的命令式文本。
- plan.deliverables 指令、order.input 缓存、卡片目标/本单/输入节重复表示相近要求；部分指令仍引用已移除的 flow.py。
- _constraints 自动带入依赖方的历史裁决诊断和沿链找到的用户答复；_handoff 再带入前单完整输入、结论与最近交付。未明确区分当前约束与历史事实。
- prepare 将全仓状态直接嵌入每个工单：实际 WO-0158-r3 卡片 429894 字节，current_repositories 的紧凑 JSON 约381705字节，包含大量非当前任务内容。
- OpenCode 适配器把全文作为一个命令行参数传递，触发 E2BIG；即使缩短当前卡片，也不能保证其他合法输入不再触发。

因此要同时整改信息来源、工单导出和传输；只删一句暂停说明或换一句提示词不能解决。

## 3. 当前有效要求如何形成

### 3.1 每项要求只在一处维护

- 目标和验收在计划目标内维护，派发时从唯一来源呈现到工单正文；记录修订用于追溯，不让实施者先翻计划拼装任务，也不维护另一份可独立修改的副本。
- 本次具体工作在工单 input 中维护，例如“仅核验三个既有提交”或“修复 B1”；不再复制整条裁决作为实施指令。
- 暂停、自动推进范围、预算和资源占用从已有结构化状态读取，不在 execution_notes、历史诊断或工单自然语言中另建一套开关。
- 任务特有的有效约束由负责人整理到对应工单/目标；修改时替换有效内容，旧版继续留在历史中。不得用不断追加“以上已失效”维持多个并存版本。
- 通用操作规范只保存稳定要求。板测调用、清理等规范可保留单份文件并按用途引用，不混入“S16还没完成”“本轮暂不恢复S17”等临时状态。

### 3.2 谁负责整理

技术负责人在设计与编制工单阶段完成选材和消歧：判断哪些背景、接口契约、设计取舍及操作约束对实施有直接影响，写入正文或明确列入必读；不能等派发时由脚本搜集，也不能让实施者从历史中自行挑选。负责人判断用户决定适用于哪些目标、哪些约束继续有效、哪些被替代，并通过 bf 事务更新有效要求及已有状态。无需用户重复批准同一事项。
脚本根据明确引用装配输入；不解析“暂停”“覆盖”等词猜测授权，也不从自然语言先后顺序推断哪条更有效。
收到用户解除暂停等明确操作时，更新既有结构化状态，不再追加一段全局提醒。工程内容发生冲突时由负责人解释并修订当前工单。

## 4. 各角色收到什么

| 角色 | 默认必读 | 按需引用 |
|---|---|---|
| 实施者 | 本次目标/验收/范围/有效约束、完成任务所必需的背景/接口契约/设计章节/操作规范、依赖产物及验证方式；由负责人事先明确选定 | 工作中实际遇到问题后需要追查的源码细节或历史证据，不附默认全量背景清单 |
| 返修者 | 当前目标、逐项关闭条件、必要回归范围和有效约束 | 对应问题的原始证据和相关审阅依据 |
| 审阅者 | 本次审阅范围、目标验收、被审版本/变化摘要、必要证据索引 | 完整快照、运行记录、需核实的历史材料；不自动注入其他审阅者结论 |
| 技术负责人 | 当前待解决问题、明确待执行操作、相关批准和影响对象 | 原始用户决定、故障链、历史工单及完整仓库观察 |
| 聊天前端 | 当前 report 的状态、ask_user 和 ops | 对应原始记录；不将 ops 自行改写成用户待决 |

执行者可了解与本任务有关的接口、依赖和明确排除项；不需要项目全部调度安排。S17只需知道自身当前允许执行和“仅完成本单范围”，不需接收S16历史收尾时对S17～S20的暂停叙述。
原始用户决定不会丢弃：有效约束由负责人落实，来源在记录中可追溯；默认工单不展示全部来源清单。只对完成本单确有用途的材料给出引用，不把所有历史原话自动作为新命令继承。

## 5. 正文与完整材料分开交付

### 工单正文

一次呈现以下内容，不在多个节重复同一长指令：

1. 工单ID、角色、从唯一来源呈现的目标/验收及本次要做的事。
2. 当前任务范围、有效约束和明确禁止事项。
3. 当前结构化调度事实：本单是否暂停、是否在批准范围、必要前置是否完成。
4. 负责人编制的必读：逐项写出具体材料、准确章节/范围和用途；需要绑定某版材料时附SHA，SHA只用于追溯。不要默认要求读取整篇设计、整份技能或完整历史。
5. 本次必要验证和交付格式。

### 完整材料

全仓观察、多轮快照、历史诊断、原始记录保持完整，放在已有 records/ 或历史存储位置。默认不把它们或它们的全量索引发给实施者；只有负责人确认完成本单确实需要其中某项时，才列为必读或附明确使用条件的参考。
选入工单的材料说明“必须掌握什么、用于哪个实现/验证决定、读哪一节”。若只需一条关键约束，正文直接写清楚，不为了溯源强迫读整份原始记录。来源和SHA可以留在审计记录，不必反复占用执行者注意力。
这不是把原来430KB的提示词机械移到另一个“必读全文”文件：由负责人在设计阶段完成必要性判断，实施者先读工单明确列出的必读材料，再执行；无需自行遍历材料仓库补齐背景。必需输入仍须完整送达，不能随机裁剪或按字数截断。
历史材料明确属于事实与来源，不能自行改变当前有效要求；需要改变执行要求时交负责人通过bf修订。

## 6. 派发、续作和长文本传输

- 从同一有效工单输入生成所有后端的导出。适配器不得重新选择或拼接另一份任务要求。
- 用后端实际支持且经验证的文件或标准输入传递正文。若某后端必须依靠代理读取文件，则使用短启动指令引用固定的完整工单文件，验证实际读到同一份内容。具体方式依据本机CLI接口验证后确定，不假定某个未验证的开关可用。
- 不把正文全文放进单个 argv，不靠截断“解决”E2BIG。启动失败必须留下明确的结构化启动错误，不只表现为 exit.json 缺失。
- 每次运行保存实际输入及SHA以供追溯；导出文件不成为另一个可编辑的当前状态源。
- 同轮续作引用原始完整工单；换执行者或新会话获取完整有效输入。有效要求已调整、旧会话含冲突要求时明确 fresh_session，不继续用短补丁让模型自行清算历史。
- 运行中的本次输入保持可追溯，不偷偷替换；用户 stop 等实时控制仍由驱动器执行。输入发生修订后，下次派发采用新输入，不自动推导产品结果失效。

## 7. 删除或收敛的现有逻辑

- 取消将全仓 current_repositories 内嵌每张卡片；保留采集和审计位置，默认不向实施者发送全量材料索引。
- 取消 _handoff 对来源输入、来源结论、最近交付的全文自动展开。
- 取消 _constraints 将全部祖先诊断/原始答复递归拼成当前执行约束；替换为负责人维护的有效约束及来源引用。
- 移除目标指令、有效input、本单正文的冗余长文本副本；模板只展示一次。
- 清理 execution_notes 中历史状态与临时恢复决定，稳定操作规范独立引用。
- 不新增自然语言冲突正则、上下文自动摘要模型或“遇到某关键词转裁决”规则。

脚本只检查字段、引用和文件是否可送达、实际调度控制、输入导出是否完整及传输协议。材料有无工程价值、旧证据是否足够、范围解释由角色判断，不增加工程门禁。

## 8. 用 S17 展示整改结果

正文应明确：

- 目标：撤下六个v1异步SDO接口及专用类型，更新绑定/桩/编译与ABI检查。
- 验收：正文呈现现行S17的完成标志，不改变指标，不让实施者从多份历史计划中重建。
- 当前状态：S17已授权且已解除暂停，前置已登记完成。
- 范围：本次S17相关实现及检查；不顺手实施其他批次，不提交、不推送。
- 操作：使用当前bf留证及相应验证规范，不再同时出现flow.py旧示例和多段覆盖解释。
- 必读：由负责人选定与六接口撤下直接相关的D17/现行接口契约段落、ABI基线及必要验证规范，说明每项用途；若指定完整文件，说明确实需要全文的原因。S12～S16的完整历史和来源索引不进入默认实施提示词。

不应出现“S17～S20仍暂停”之类已被替代的命令，也不注入其他任务的全仓脏文件清单。

## 9. 验证与迁移

先形成新旧输入对照样本供审阅，再实现代码。除验证有没有丢字段，还必须审阅“每项内容为什么对本单必要、是否仍有效、关键约束是否显眼”；这由负责人/审阅者判断，不建立脚本的语义门禁。

必须通过以下行为用例：

- S17从暂停到解除后，新的执行输入只呈现有效状态；历史原文仍可从记录查到。
- 多次裁决、拒绝后改向、返修、备用执行、重启和换会话均不丢必要约束，也不重新激活已失效约束。
- 普通实施、专项审阅、返修、裁决各自收到正确范围，不通过祖先全文继承扩大任务。
- 用户新要求影响多个目标时，负责人明确更新这些目标；脚本不按目标名猜测或静默漏传。
- 加入大量其他任务的脏文件不放大当前工单正文；全部观察仍在证据材料中。
- 使用本次约430KB输入及更长测试数据验证传输保真，不调用真实模型进行离线测试，不丢字符、不E2BIG、不虚报已启动。
- 假CLI实际读取到目标文件/输入，与留存SHA一致；必读的具体范围、用途和重点约束完整送达。真实执行者须先读必读；脚本不声称能够证明模型已理解内容。预算、停止、资源锁和独立审阅回归保持。
- 字段/产物索引不完整属于派发工具错误；不假装能用机械检查证明自然语言要求无矛盾。

现有任务由负责人逐项整理当前要求及来源，特别核对S17当前授权、范围、旧flow.py引用和必要验证；生成迁移差异，经bf事务落实。历史工单、运行、批准、测试记录及真实消耗不改写，不追加或重置额度。
S17的E2BIG调用仍是CLI未启动的工具失败；第一轮卡片冲突另留负责人核查，不在此次方案中擅自退款或宣布产品通过。

## 10. 工单模板与技术负责人规范同时约束

整改不是只限制模板长度，而是把选材责任前移到技术负责人设计阶段。

### 工单模板必须表达

- 要做成的结果及完成标志，直接可读，不只给目标ID和外链。
- 与本次实现直接相关的背景和已定取舍；只写影响实施的内容，不写项目发展史。
- 允许范围、必要依赖/输入和当前有效约束。
- 必读材料及准确阅读范围、用途；关键禁止事项在正文直接说明，不埋在引用深处。
- 必要验证和交付要求；发现范围外事项如何交回负责人。

模板不预置“所有历史/所有设计/所有规范都要读”的占位要求，不自动补入祖先工单或全仓资料。没有必要材料时可不列，不为凑模板栏目制造背景。

### 技术负责人技能文档必须明确

- 编制前读懂相关设计和接口，自己完成背景提炼、范围解释和已有授权落实，不把查清任务的责任转交实施者。
- 对每项拟放入上下文的材料，能说清“不知道它会导致哪个具体实现/验证错误”；没有直接用途的从默认输入移除，不只是改标为参考。
- 必需设计/约束在编单时就进入正文或必读，不能因“按需读取”而漏掉。阅读范围以相关章节为准，不默认扩张为整篇。
- 约束更新时整理一份当前有效要求，保留必要来源供追溯，不继续追加覆盖语句。不自行把历史诊断、已失效的批次限制推广为全局规则。
- 范围、验收、验证方案和副作用边界在设计阶段说清；派发输入自洽、重点显眼。普通派发不增加一次模型摘要或新的审批流程。
- 技能规范自身也要精简与消歧，必要的共同要求集中维护。工单只引用适用章节，避免迫使每个执行者反复读全套规范。

## 11. 必须保留的重点约束

以下内容在精简后的技能规范中有明确归属；与本单相关的关键要求在正文可见，其余通过负责人选定的必读章节传递。不是每张工单照抄整张表。

| 必须保留的约束 | 主要归属与传达方式 |
|---|---|
| 按批准目标自主推进，范围内可继续的工作不提前交回；不顺手扩需求或他批改动 | SKILL/角色规范；工单写本单范围及真实停止条件 |
| 用户停止、明确授权、预算、资源互斥及必要用户决定边界有效；已有批准不重复询问 | 结构化控制与负责人规范；只把本单适用的权限/操作边界呈现给实施者 |
| 质量、范围合理性、证据充分性归审阅者/负责人；脚本只做机械协议与状态检查 | SKILL/审阅与负责人规范，不恢复快照/退出码等工程推断门禁 |
| 独立审阅，不自审；返修只处理问题及直接回归，不借审阅扩大范围 | 角色及审阅规范；返修单列具体关闭条件 |
| 以真实代码、实际目标行为及可复现验证为证据；模拟或登记成功不能冒充产品通过 | 工程规范；工单明确本次验收与必要验证 |
| 失败、未运行、限制、版本差异如实报告；原始运行/快照与SHA保留，不伪造或覆盖失败 | 工程规范/记录机制；不要求全文历史进入执行提示词 |
| 最小改动、复用现有实现，只做必要验证，不为假想情况增加平台、测试和门禁 | 工程规范及负责人设计职责 |
| 正式状态只经bf事务维护，保留幂等和审计；换单/换上下文不重置真实消耗 | 脚本与运维规范；实施者不用承接调度内部细节 |
