# 工单重构审阅（2026-11-07）

审阅基线：技能仓库提交 `3f4cdc7`，审阅前工作区干净。范围为当前入口、设计、角色规范、bf 实现及离线测试；未启动项目任务，未调用真实模型。

对该基线的结论：脚本调度、工单承载工作的方向可保留，但尚不能认为保留了原有的核心裁决和上下文保证。发现 7 项问题，其中 6 项 P1、1 项 P2。以下记录修复前的依据；修复状态见末节。

## 发现

### 1. [P1] 换工单即可重置实施额度，并绕过作废依赖工单的用户审批

位置：`scripts/bf/policy.py:35`、`scripts/bf/register.py:32`、`scripts/bf/register.py:60`。

`used(order)` 只统计本单 runs；负责人 `open implement` 时会得到一张额度完整的新单。`_needs_user()` 又把 review/release 从“有依赖方”的检查中排除了，允许负责人自行作废只被审阅与放行依赖的实施单。这与设计 I2、“实施按交付目标计额”及“作废有依赖方的工单须问用户”冲突。

复现：D1 配置 primary=1、backup=0、lead=1，两轮技术失败后进入 decide；负责人作废旧实施单并为 D1 开新实施单。结果旧单 `superseded`，新单又可用 primary，且没有 ask_user。即使不作废旧单，另开实施单也会获得全新额度。

建议：额度归属于稳定的交付目标/返修周期，工单只引用额度归属；开单、换会话、重建均不增额。作废审批直接按依赖关系判断，不按依赖方类型排除。

### 2. [P1] 实质修订计划后，旧实施与旧审阅仍可直接支撑放行

位置：`scripts/bf/register.py:127`、`scripts/bf/routing.py:259`。

修订仅安装新计划、校验用量、调用 `sync_plan()`；后者按已有 key 判断“不必开单”，不处理同一目标的指令、验收、审阅组成员发生变化。已有工单的 input 也保留旧内容。

复现：D1/D2 完成，R12 RELEASE；在 B1 放行前批准修改 D1 的 instruction 和 acceptance。修订后 D1 与 R12 仍为 done，工单内指令仍是旧的 `do d1`，B1 release 仍可派发。新验收既没执行也没审阅。

建议：明确交付目标的契约版本。实质修订生成新版本，旧记录保留；受影响实施、审阅和下游放行必须等待新版本完成。不要只用目标 ID 判断幂等。

### 3. [P1] 一组审阅触发返修后，另一组已通过的审阅不会失效

位置：`scripts/bf/routing.py:193`、`scripts/bf/routing.py:236`。

`link()` 仅处理 implement，`open_repairs()` 仅让提出问题的 review 等待 repair。它没有使同一交付目标的其他已通过审阅失效。设计 §24.5 明确要求实施或返修都重新触发相关审阅，第三方同样适用。

复现：D1/D2 同属 R12 和第三方 T12；T12 先 RELEASE，R12 随后提出 D1 阻断。D1 返修完成、R12 复审通过后，T12 仍只有一张 done 工单，B1 已可放行。最终改动从未经过第三方重审。

建议：审阅通过绑定目标版本集合。implement 与 repair 都通过同一版本变更入口使相关审阅过期，放行只接受当前版本的通过结论。跨批审阅应更新审阅组所属批次的放行依赖。

### 4. [P1] 裁决开出的前置工作，不会阻止被裁决工单立即重跑

位置：`scripts/bf/register.py:19`、`scripts/bf/register.py:60`。

decide 合法交付后立即 done；open 动作只创建新单并联入审阅/放行，不把 waiter 与新单建立等待关系。卡片虽写“先修复再重试”，脚本没有对应的可恢复状态。

复现：D1 待裁决；负责人决定为 D1 开一张前置实施单。decide 完成后原 D1 不依赖新单，并在串行派发中先于新单重新变为可运行。它可能重遇相同问题、提前消耗额度，甚至重新裁决。

建议：裁决明确区分“已诊断”和“处置已完成”；前置处置建立显式依赖，完成后才解除原工单等待。决定中不应让模型猜测未来工单号来拼接依赖。

### 5. [P1] 自动生成的版本快照没有纳入证据哈希保护

位置：`scripts/bf/api.py:107`、`scripts/bf/routing.py:216`。

登记先为角色引用的证据建立哈希，再生成自动 snapshot；新快照只存入 `run.snapshot` 和 `run.version`。完整性检查只遍历 `run.evidence`，审阅固定版本只核对路径文本是否出现。

复现：带 repos 的实施改动生成自动快照；随后修改快照 JSON 内的 diff。`broken_evidence()` 仍返回空列表，快照路径仍是合法的审阅版本依据。这破坏 I5 的固定版本和哈希保证。

建议：版本快照与验证记录共用不可变证据引用；生成快照时同时登记哈希，依赖检查和放行使用同一检查入口。

### 6. [P1] 等待用户时驱动器退出，回答或恢复并不会让任务继续

位置：`scripts/bf/runner.py:175`、`scripts/bf/cli.py:109`。

`run_until_idle()` 在没有进程在途、没有可派发工作时退出，未区别“全部完成”和“等待用户”。`answer`、`resume`、`retry` 只改文件状态，不启动驱动器；前端提示词也没有要求这些命令后确保驱动器重新运行。

复现：D1 进入 ask_user，其他可运行工作完成后 run 退出；用户批准后 D1 已可运行，但 `driver.alive=false`，没有角色继续执行。现有测试通过再次显式调用 `run_until_idle()` 掩盖了真实 CLI 生命周期中的断点。

建议：明确选择一种生命周期契约：驱动器等待可恢复事件，或前端在回答/恢复/运维重试后统一确保单实例 run 存活。应覆盖真实命令组合，不能依赖人工重新运行测试驱动器。

### 7. [P2] 裁决卡丢失已有结构化上下文，负责人无法仅凭卡片诊断

位置：`scripts/bf/cards.py:134`。

decide 卡只渲染 trigger、subject、run、issue/answer 和 evidence，遗漏 `subject_input`、运维 `problem/note`、受保护改动 `paths/snapshot`、设计漂移的受影响 deliverables 等已登记内容。角色又被要求只读工单卡、不读状态文件，新会话因此缺少定位依据。

复现：连续两次 abandon 记下 `UNIQUE_AUTH_ERROR`，前端 escalate 带 `UNIQUE_NOTE`；裁决卡不含这两项，也不含源实施指令 `do d1`。故障详情虽然存在状态中，却没有交给承担诊断职责的人。

建议：统一定义源工单的交接材料，包含原指令、当前版本、触发事实、相关证据与已批准约束；以引用和必要摘要传递。裁决/返修/接替执行者使用同一交接材料，保持新会话与完整输入同时成立。

## 对重构目标的判断

- **角色定义**：负责人规划/诊断、执行者实施、审阅者独立审阅的分工已写回文档；卡片也链接角色规范。但 `roles.md` 开头“不需要读其他规则文件”与卡片“规范”节及入口的规定不一致，需统一。
- **核心裁决链**：decide → ask_user 的骨架存在，实施阶梯和返修独立额度也有实现；额度归属、裁决处置依赖和版本失效尚未闭合，不能仅以有这些工单类型认为链路保留。
- **上下文维护**：首审新会话、阶段切换新会话、复审续接等规则集中于 context.py，是合适的组织方式。但上下文还包括交接材料，不能只检查 session ID。另需核对长度阈值语义：adapter.py 当前记录单次 CLI stdout 大小，而不是同一会话累计长度，长期多轮会话可能一直达不到 300 KB 阈值。
- **脚本复杂度**：当前 bf/*.py（含适配器测试）共 2870 行，按存储、路由、门禁、上下文拆分，主循环比旧模型编排清楚。但设计已连续追加运维、证据、完整性和卡片条款，部分实现再次按类型/触发场景分支。建议围绕额度归属、契约/产物版本、裁决因果依赖、交接材料四个概念整理，不再为每种故障各加一个状态补丁。无需恢复 v1 的编排者、双台账或全套 hook。
