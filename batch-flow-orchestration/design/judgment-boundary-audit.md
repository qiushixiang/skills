# batch-flow 脚本判断职责整体审阅

日期：2026-11-08。状态：设计审阅结论，未实施。范围：scripts/bf 的状态、计划、预算、派发、交付、快照、证据、裁决、恢复主路径；同时核对 CLI 适配器的传输/权限检查与角色规范。不是对所有前端 UI 和外部 CLI 的完整缺陷审计。

依据用户最新裁定：快照及 SHA 用于供审阅者判断版本与证据关系，不因快照事实直接阻断工程推进；修复合理性由审阅者判断。现有其他用户授权、停止、预算和宿主权限不因此被取消。

## 1. 总体结论

问题不局限于快照。当前多处使用可机械计算的替代指标，推断需要工程知识的结论：退出码替代验证充分性、字段位置替代授权含义、代码变化替代实际进展、文档文本差异替代交付失效、命令形态替代工作性质。
计算指标是机械操作，但由指标推出工程结论不是完全机械的检查。继续增加例外列表、正则和场景分支，会同时产生误拦截与漏判断。

脚本只维护可确定的协议和流程：数据结构、对象引用、状态事务、已批准的预算/停止/资源占用、角色身份、显式依赖、模型调用传输结果。审阅者判断交付是否成立；技术负责人判断方案、阻塞原因、范围与影响及协调处置；用户判断新增承诺、权限和预算。

## 3. 应保留的机械检查

- JSON/协议字段类型、必填项、结果枚举、动作字段、对象 ID 和引用存在、依赖图无环；发现错误按协议错误报告，不冒充产品失败。
- 排他锁、事务、CAS、原子写、幂等、运行 ID、追加历史、不重复回收、不运行两次同一条状态操作。
- 用户明确 stop/hold、已批准自动范围、预算累计、并发上限、资源互斥；按照明确计划选择角色和顺序。
- 作者与审阅会话身份隔离、明确要求的新会话、上下文长度和后端兼容策略。
- CLI 是否启动/退出、有无合法会话及传输结果；宿主实际权限与明确授权一致性。工具故障和产品失败分开登记。
- 工单输入的完整导出：必要字段与引用没有在模板/适配器中丢失；这能机械核对，任务是否完成则不能。
- 按审阅/负责人已登记的结论执行返修、复审和放行；放行只确认既定前置结论均已登记，不重新评价代码或测试。

“保留机械检查”不意味着其当前实现必然无 bug；本次重点是确定职责边界，避免将工程判断写成更多规则。

## 4. 简化原则

不把工程判断改为另一套更复杂的通用规则引擎，也不把每条警告自动开成新阻塞工单。

统一为三步：采集事实 -> 将事实与工单完整交给指定角色 -> 按角色结构化结论做状态转换。
正常审阅能处理的事实并入正常审阅；执行者明确无法继续、角色意见冲突、范围/权限需要裁决时才交负责人。
预算上限等保护机制继续有效，但名称应如实反映“次数用尽”，不能宣称已机械证明“无技术进展”。

角色结论至少说明结论、依据、影响对象和处置。脚本检查结构与操作引用，不用关键词、日志正则或字段路径判断理由是否工程上成立。
新增预算/权限和用户明确确认点仍须用户决定；负责人不得以文字声明绕过数值或宿主权限。自然语言范围解释由负责人承担，必要时独立审阅，脚本不伪装成语义授权审核者。

工单是执行要求的依据；卡片只是导出。不要再建一份独立任务台账或补充指令体系。
事实异常（旧证据缺失、版本变化等）必须显示，不能隐瞒；但异常显示不等于脚本有权判产品失败或全局暂停。

## 5. 最小行为复现

本次仅在临时目录和任务状态的内存副本验证，未写项目状态：

- /usr/bin/true 生成的无关 record 会通过 fresh_pass，说明“新且退出 0”不等于验收证据充分。
- 归一化计划中只替换 instruction，甚至写成取消原验收/改做其他项目，internal_revision 仍返回 True。该文本与原验收本身冲突；脚本无语义判断能力，结构检查不能证明授权内。
- 为既有对象新增诊断证据及改变约束，decision_progress 摘要不变。这里只证明指标未覆盖这些事实，不声称所有新诊断都构成实质进展。
- 前次复现已证明纯提交保护路径误拦截、已脏文件执行位变化漏检、最近一次增量遗漏前轮快照及专项指令未传。

## 6. 后续改造范围

先按以上职责清单删除/降为事实提示的工程推断，再统一工单信息传递，不围绕每个误判新增特例。
测试验证两面：机械协议/预算/停止/独立审阅仍受保护；相同工程事实在多场景下均交正确角色而非自动否决。
测试必须覆盖有效旧证据、预期非零反例、无关退出 0、文档措辞变化、环境恢复但源码未变、跨组件根因、历史证据异常及常规上下文切换。
修改 SKILL/设计/角色规范中“交付合法性由脚本判断”的措辞，明确仅指协议及状态操作合法性，不指工程验收成立。
本次是审阅与设计产物，未更改运行代码，未运行真实模型、未恢复任务，未修改现有计划或权限。
