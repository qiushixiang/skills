# 执行轮次

新计划使用 `policy.execution_model: "cycles-v1"`。每个交付目标配置主执行者、备用执行者、技术负责人各自最多几轮；每轮包含一次实施交付、首次审阅，以及首次审阅要求修改时最多一次原作者返修和复审。首次审阅通过即结束；返修复审仍不通过，本轮结束，当前执行者有剩余轮次则开始下一轮，否则依次切换备用、负责人。没有可用执行者时转负责人处置并暂停受影响路径，不增加额度或擅自通过。

```json
{
  "policy": {
    "execution_model": "cycles-v1",
    "rounds": {"primary": 2, "backup": 1, "lead": 1, "coordination_attempts": 2},
    "overrides": {"S24.D": {"primary": 1, "backup": 1, "lead": 0}},
    "continue_limit": 2,
    "context": {"max_session_kb": 300}
  }
}
```

- `primary` 是主执行者轮次，`backup` 是备用轮次，`lead` 是负责人亲自实施的轮次。未配置备用角色则该阶段不参加执行轮次计算；每个目标至少有一个可用执行者轮次。
- 不配置 `implement`、`repair` 或 `review` 数量，混用会拒绝。目标 override 仍用上述三个字段；审阅组不配置作者轮次。协调次数、CLI 重试与同次调用续作继续独立配置，不是额外的交付/返修机会。
- 一次实施内部允许正常修改、编译、调试和有界续作，不按命令数计轮。返修要一次处理本次审阅列出的全部阻断项，不按问题数量追加次数；复审不是新返修机会。不同审阅组共享同一目标每轮的一次返修权益。
- 评审中的“方案级”标记不静默丢弃原作者的返修机会；需要变更方案或无法处理时按移交协议交负责人裁决。技术负责人实际兜底的交付由独立审阅者检查，不自审或自裁决。

## 记账与恢复

初次实施调用启动时预占该作者一轮，运行记录保存本轮 ID；本轮返修引用同一 ID，不另扣执行轮次。CLI 真实调用、输出和失败仍全部记录。只有适配器明确证明整次未启动，且没有有效已执行片段时免扣；返修未启动不消耗本轮返修机会。新模型不能通过 settle 抹去已执行轮次。

新建实施/返修工单采用 delivery-v2：只填“交付状态：已交付 | 未交付”。已交付直接进入独立审阅，不经过负责人质量预审。未交付及缺失/矛盾协议都保存原始输出，按本次运行开立唯一的负责人结算裁决，不自动补格式或续作。裁决只处置未完成原因、执行去向与轮次归属，不判交付质量、不放行审阅。每次未交付有自己的裁决，不累计成同一问题次数上限；每张裁决的非法协议修正和协调尝试仍受已有上限约束。

负责人用 `{"continue_run":"WO-n-rN","reason":"具体下一步"}` 恢复本裁决对应的最新未交付运行。驱动器保存一条新调用记录，绑定原执行者和原轮 ID，phase=continue，不增加实施轮次，不增加本轮交付/返修机会，不覆写原运行。正常续作没有次数上限，也不受 continue_limit 约束；停机重启保留关联和去重事实。原作者尚能完成时应在当前调用内持续工作，不能把裁决当成进度汇报入口。

`retry` 表示结束原轮的当前尝试，再依已有轮次或尚未使用的原作者返修权益恢复；已尝试的返修机会不因 retry、换工单、计划修订或重启恢复。CLI 确认结束但不可用时同次调用重试一次，连续两次异常按既定阶梯换人；仍在运行则等待，状态不明不重派。用户停止始终优先。

技术裁决确定可执行下一步，不指定执行者。continue_run 绑定原作者；retry 由驱动器先保留本轮尚未使用的原作者返修，否则按主执行者、备用、负责人顺序选择有剩余轮次者，历史上曾进入较后阶段不禁止回选。历史裁决携带合法的 performer 字段可继续收取，但 cycles-v1 不用该字段覆盖驱动器选择；legacy-v1 仍按原显式选人协议。

自动 CLI 异常切换仍只向当前失败角色之后寻找，不自动来回重派；技术裁决恢复才重新按剩余轮次选择。裁决登记前在隔离状态中核验整包处置（包含增额、结算、授权）后的可派发条件；不可执行的 retry 按不合法裁决反馈负责人有界修正，不执行部分动作、不让驱动器退出，也不自动增加额度。

负责人协调与角色间裁决不占作者执行轮次，但仍受独立协调次数上限约束。增额只增加执行者轮次，需要批准；例如 `bf grant S24.D --primary 1 --approval F`。不单独追加返修或审阅数量。

兼容边界：已存在的 intent-v1 工单和在途运行按原卡、原协议回收；不把旧“继续/移交”输出解释成新协议。新建 cycles-v1 工单使用 delivery-v2；legacy-v1 保持原协议。continue_limit 仍用于历史协议续作以及审阅/裁决非法协议修正，不限制 delivery-v2 的正常同轮继续。

## 独立审阅

审阅随交付和返修派发，不设置或计算独立审阅容量，不累计审阅额度，也不以历史审阅调用次数阻止实施、返修或后续审阅。每轮一次交付和至多一次原作者返修仍由执行轮次约束；计划规定的全部常规/第三方审阅组、依赖和作者独立性继续生效。缺少独立审阅工单仍阻止实施派发。

审阅调用本身的 CLI 故障、非法协议等保留原恢复方式和次数约束，耗尽时进入协调或运维处置；不因取消容量而无限重试。已批准增加作者轮次时无需调整审阅额度。历史审阅调用、结果和证据保留供审计，不用作独立容量扣账。

## 在原计划追加新批次

无需为新旧计数规则另建任务。原计划保持 legacy-v1，在**新增交付目标**上声明执行策略即可：

```json
{
  "deliverables": {
    "S24.D": {
      "execution": {
        "model": "cycles-v1",
        "rounds": {"primary": 1, "backup": 1, "lead": 0}
      }
    }
  }
}
```

这里只展示交付目标的执行策略，其他必需目标字段仍按计划编制。目标级 execution.rounds 只允许 primary/backup/lead，不再在 policy.overrides 重复配置该目标。协调上限继续使用计划级策略；CLI 与角色增额都修改同一处目标轮次。

所有派发、记账、返修、卡片和报告统一按目标的有效模型解析。审阅组继承成员模型；一个组不混合两种模型，需要时按新旧交付目标分别建组。原有组不因新增批次自动重开或增加职责。

## 版本边界与执行范围

没有旧额度字段的新计划默认 cycles-v1，建议显式声明。已有带 implement/repair/review 字段的计划按 legacy-v1 保留原计数。新增目标可以声明 cycles-v1，不改变任何旧目标或历史用量；旧目标及已有审阅组不得切换计数模型，移除再添加同名目标也不能绕过历史版本边界。

整个已初始化计划的默认模型不原地切换。若确需改变旧目标的计数规则，应另定明确迁移方案，不把新增目标当作旧目标的替身重置额度。

同一份计划可用 envelope.batches 选择只推进指定批次，保留全部正式依赖；选择后续批次不会自动跳过未完成前置。切换范围不需要另开工单目录或切换驱动器，但调整范围须有用户授权，且不终止在途工作；全局 stop/resume 与单批 hold 继续独立生效。
