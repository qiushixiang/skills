# 与其他 agent 协作：派发、回收与汇报

本文是宿主无关的派发、回收、用户同步和计时规则。当前 dispatch_owner 用宿主工具调用角色，flow.py 只给指示与登记，不代调模型。具体调用形态按宿主只读一份：[Claude Code](claude-code.md) 或 [AGY 与 Codex](hosts-agy-codex.md)。角色边界见各角色文档，上下文隔离见[上下文规则](contexts.md)，模型来源见[提示词规范](prompts.md#0-编排者入口模型提醒)。

## 1. 派发前

运行 observe 或 status，选合法动作；核对批次/节点、被审对象版本、授权、剩余预算、读写范围及上下文归属。编排者只机械核对路径、存在性、Git 状态/版本、退出码和关联，不读业务实现、不分析 diff、不运行探索性产品命令。

派发内容按[提示词规范](prompts.md)只发通用头、本角色段与节点差异，写明工作目录、写权限和谁保存结果：可写执行者在指定范围落盘；只读审阅角色返回一次原文结论，由派发责任人原样保存，不为写报告扩大其权限。首派指令必须包含的内容见[批次指令与设计书对应](protocol-plan.md#批次指令与设计书对应)；接管阶段按 status 的 executor_stage/call_config 派发，规则见[执行者接管](protocol-budget.md#执行者接管)。

先 start 再调用；会话未知用 `pending:<调用标识>`，finish.call 补真实会话。原始调用记录保留展开提示、起止时间、退出码与结果；工具已有记录时不另存 prompt/session/summary 文件。

### 实际派发与交还控制权

“决定已闭环”“下一节点 READY”“start 成功”都不等于宿主已调用代理。dispatch_owner 在当前活跃轮次继续：重读 next → 选授权内动作 → start → 实际调用宿主工具 → 取得真实 agent/session/进程回执 → 启动计时 → register_dispatch。不能用“准备就绪，将自动派发”代替工具调用；没有真实运行任务，就没有可依赖的结束通知，定时器也不会补派。

register_dispatch 关联未结束 attempt、真实工作 handle、不可变宿主回执，以及二选一计时回执（原生 timer_id/owner_conversation_id/due_at，或脚本 timer_handle/timer_ticket）。pending 不能充当 handle，可变的 ticket 不当不可变回执。到期汇报重启计时时可保留同一 handle；任务快速返回直接 finish 并取消计时。没有原生回执文件就原样保存已收到的回执，不能自写“已启动”。

每次准备结束本轮/交还控制权时执行 `python3 <技能目录>/scripts/flow.py --store <台账> pre_yield`：

- CONTINUE（退出 1）：还有授权内可推进动作，或运行尝试缺真实回执、进度到期；先完成对应调用/汇报/恢复。
- STALLED（退出 1）：未完成、无在途且无可执行或用户待决动作；检查依赖或裁决，不凭“等待”无限停留，不自改门禁。
- WAIT_HOST（退出 0）：有运行尝试和未到期计时；仍需核对句柄有效、能收到结束通知，票据不证明进程存活；不支持通知时短轮询。
- WAIT_USER（退出 0）：只剩需用户答复的动作（含授权、模型指定）；给出具体请求与依据。
- COMPLETE（退出 0）：全部完成，回收残余定时并交付。

pre_yield 只读，不扣预算、不调模型、不验证进程存活；只有宿主接入 stop hook 才能强制拦截，未接入也须主动执行，不谎称已装守护。用户暂停/停止或宿主中断优先，说明最后状态并保留现场。

“说了要派发却没进展”时，先查最后工具调用、attempt、真实句柄和 ticket，区分未 start、start 未调用、已派发未登记、工具已退出、计时失效；确认没有相同写任务仍在运行后才补派，不看到 pending 就新建第二个执行者。编排漏动作不归咎于执行者。

## 2. 结果回收与分流

1. 核对实际会话/模型、退出码、非空原文、权限拒绝、产物存在，以及输出属于本 task/attempt/版本；技术正确性由责任与审阅角色判断。
2. 有效交付由 dispatch_owner 按[交付形态](prompts.md#8-结果与请求的最小形态)用 finish 代交，actor 为实际责任角色（lead 阶段为 architect），补 call_id、实际 timing 与 triggers；不直接编辑 flow.json。
3. 无效调用与启动失败按下节分类；真实技术失败、证据不足分别登记 FAILED/WAIT_EVIDENCE，不能用 INVALID 免记技术消耗；预算分类与续作见[技术预算](protocol-budget.md#技术预算记账与续作)。
4. 审阅结论缺少与本批 AC/契约的关联时请原审阅角色澄清，不自行降级；本批 FIX_REQUIRED 交原执行者定向修复并按原节点复核；阻断尺度见[审阅边界](engineering.md#审阅边界与问题处置)。
5. ARCH_DECISION_REQUIRED 或 REGISTER_DECISION 按[诊断恢复](../workflows/recovery/SKILL.md)登记 signal 并派技术负责人。

进程中断而结果未知时，先查原进程、工作区和已存输出，不盲目重跑写入。CAS 冲突先重读；字段或载荷错误退原角色，只可修正派发模板格式，不改角色已返回的 plan/结论，不改 flow.py 或放宽校验。

### 启动失败与无效调用

- 尚未开展有效工作、因权限/认证导致空回复或无产物：保留原始结果登记 INVALID；交 architect 核对 environment 免扣，在实际执行环境取得新的能力证据后有限批准 resume_attempt，start 用 status 给的 continuation_of；不直接换人，也不在条件未修复时原样重试。
- 已有实质实现、仅验证命令被拒：保留产出，登记 WAIT_EVIDENCE 等真实状态与最小缺项。
- 修正启动条件后仍无法合法执行：交技术负责人按工具阻塞处理，编排者不接手实施；环境重试次数与技术预算分开检查。

## 3. 用户同步与长任务跟进

编排者把角色原始结果转成用户看得懂的进展。每个设计、实施、审阅、裁决、验证、提交环节结束且核对结果后立即同步；串行紧邻的机械登记可合并一次说明，但不遗漏审阅问题、失败、关键决定或版本失效。授权内同步后继续推进，只在确需用户决定时提出具体请求。

环节结束说明（按相关性简述，不机械填“不适用”）：

- **本轮交付**：中文名称、实际完成与未完成；区分设计已交与已审、代码完成与验证通过、本地完成与已上传。
- **验证结果**：哪些目标已由真实构建/测试证明，哪些失败、受阻或未运行及最小缺项。
- **审阅问题**：覆盖对象/版本与结论；逐项列阻断问题的实际问题、影响、归属与关闭条件；非阻断建议去向；R2 交代已关闭、未关闭和新增问题，保留原文链接。
- **决定与变化**：裁决内容、原因与影响；哪些旧审阅/证据已失效；执行者接管的原因、接管角色/模型与剩余工作。
- **投入与后续**：本轮耗时（无实际调用时间时注明登记区间）、技术预算已用/剩余及免扣/续作；下一步责任人、动作、前置条件，是否需要用户决定。

```text
<批次中文名 / 本轮角色与轮次>：<结论>，<完成内容或固定版本>。
验证/审阅：<实际结果、具体问题与影响、已关闭及遗留问题>；原文：<链接>。
投入/变化：<本轮耗时与预算；有免扣、续作、接管或授权变化时讲清>。
下一步：<谁处理什么、关闭条件/当前门禁；仅必要时提出用户决定>。
```

### 每 10 分钟汇总全部在途任务

运行期间任一在途任务距上次用户可见同步不超过 10 分钟；并行任务合成一条，逐项给中文名称、角色/阶段、累计运行时间、最近核实的进展、当前动作/等待、阻塞与责任人、下一检查点。完成、异常、需要用户操作时即时报告；用户询问时也即时报告。

来源限于角色消息、调用事件/状态和明确日志；不为凑进展扫描源码、做诊断或跑产品测试。有运行中的子代理/子进程时，从已登记派发记录和句柄核对实际在途项，逐项说明用途与所属批次、具体目标、已完成步骤、当前动作与卡点、最近观测时间与下一检查点；代理在等它启动的构建/测试时说明二者关系。没有中途输出就写“最近于<时间>观测到<事实>，此后暂无新的可核实进展”，不猜内部思考或完成比例。

连续两次定期同步无新增可核查进展时，向责任角色索取一次有界说明（正在做什么、最后有效结果及时间、卡点、下一步、继续等待的依据）；无法解释或同类失败重复时交技术负责人。状态询问不另开技术轮次；不因暂时无回复重派写任务、换模型或强杀可能正在写现场的进程。

派发后用可返回句柄的异步/后台调用，单次阻塞等待不超过 60 秒。`flow.py feedback` 只是一次反馈记录，不是定时器，也不证明用户已收到；必须在用户可见会话中汇报。新会话接管时先读最近同步与在途状态，过期先补报；全部完成后停止定期汇总；宿主无法持续运行时说明最后观测时间与限制。

### 原生计时与脚本兜底

取得真实工作句柄后，优先用宿主实际暴露、能唤醒负责会话的一次性原生 schedule，600 秒到期；条件触发时核实不会因无关事件提前取消。到期汇报全部在途任务并按需新建下一周期，工作结束、失败或取消时取消定时。register_dispatch 用 timer_kind=native 并给真实 timer_id、负责会话 ID、due_at 与不可变回执。各宿主能力见[宿主接入](../workflows/host-setup/SKILL.md)。

无原生调度时，用能返回结束通知的异步宿主工具前台运行 `python3 <技能目录>/scripts/progress_timer.py wait --ticket <绝对唯一临时路径> --task <任务ID> --goal "<具体目标>" --handle <真实工作句柄>`，登记 timer_handle、timer_ticket 与原始回执；`PROGRESS_DUE` 后汇报并用新 ticket 重启，结束时 `progress_timer.py cancel --ticket <路径>`（回收 `TIMER_CANCELLED`，不杀工作进程）。不用 nohup 或 `&` 丢失结束通知；宿主无通知时主动短轮询，不承诺离线提醒。原生与脚本一次只保留一种，切换前取消旧触发器。

## 4. 续接失效与并行

续接失效时记录原因，在预算与节点策略允许下用原始材料重建会话，以 replacement_reason 登记并保留旧 ID 关联；重建不清零预算。新会话重读当前文件；R2 提供问题清单、修复差异、当前验证与未决项，不凭旧记忆关闭问题。

技术负责人按依赖与共享文件安排并发：独立批次可并行，每个共享文件单一写入者，冲突写入串行；确需独立工作区按宿主能力与授权安排，不要求所有任务建 worktree。不并发驱动同一执行/审阅会话，不因并发缺槽跳过门禁。

除已委派为局部 dispatch_owner 的技术负责人外，角色不得再派角色；任何角色不得自行改模型、追加预算或扩大范围。角色调用不可用或模型不符时记录受阻交技术负责人，不静默改由主会话代做或换模型。编排者写入限于管理操作、请求转交、原始调用/交付记录；record/snapshot 不扩大其权限，产品验证与差异固化交执行者。
