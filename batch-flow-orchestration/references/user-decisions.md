# 用户确认边界

技术问题先由技术负责人诊断和裁决。只有需要新增用户决定时才生成 ask_user。沿用 v1：严重阻塞、范围受阻、预算耗尽本身不自动生成用户等待；已有授权在有效范围内持续生效，不重复请求。

## 六类用户决定

| category | 场景 | 需要用户决定的内容 |
|---|---|---|
| commitment | 改变交付承诺 | 增删目标、降低验收、将必需项目改为受限或延期、改变已承诺公共接口语义，或减少必需独立审阅 |
| authority | 扩大授权边界 | 跨出授权范围、突破用户明确禁改边界、申请新宿主权限，或执行尚未获准的提交、推送、发布等行为 |
| budget | 增加预算或资源投入 | 负责人诊断后确需追加额度、采购设备或使用新的付费资源，给出具体数量和理由 |
| risk | 接受残余风险或新责任 | 拟保留的临时方案产生原约定外的限制、风险或维护责任，需要用户接受 |
| information | 缺少不可代替的用户信息或选择 | 已有资料无法确定的业务需求、优先级、账号或设备选择；技术上能自行核实的事实不在此类 |
| checkpoint | 用户明确设置的确认点 | 如“设计完成后等我确认”“某阶段先暂停”；必须来自用户已有明确指令，不能临时创造用户门禁 |

类别是语义责任，不是填一个枚举即可把技术困难转给用户。负责人必须先核查既有资料、批准和可行恢复路径，再提出真正待决事项；脚本只核对结构，不假装理解自然语言是否合理。

## 不生成用户待办的情况

- 普通缺陷、测试失败、证据不足、角色意见冲突：实施/返修或负责人裁决，必要时独立复核。
- 已授权范围内局部、可撤销、可验证的修复：负责人确定有界方案后实施和审阅。
- 额度耗尽：先交负责人判断；只有确需新增投入才提出 budget 决策。
- 工具故障、批准未落实、权限登记遗漏：运维处理，沿用既有授权，不重复询问。
- 技术实现调整、重试、换上下文、处理失效工单：保留验收、预算和必需审阅后自行处置。不能以作废有效依赖或审阅冒充机械调整。
- 裁决/重试次数用尽、连续无进展、负责人暂时无解：暂停受影响路径并报告原因和最小缺项，不问“继续吗”，不要求用户解决技术问题。独立的已授权工作继续。

## 动作和报告

负责人主动提问用 `ask_user` 动作，并附 `user_request: {category, decision, recommendation, impact}`；分别说明类别、具体决策、推荐方案及代价/不决定的影响。可选 options；信息缺项允许自由文本回答。不接受只有“继续吗”而没有上述结构的动作。

权限、预算、实质计划变更仍使用 authorize、grant、plan_revision 等结构化动作，脚本按真正越界动作自动归类并整包请求批准，不再额外混入 ask_user 造成重复提问。批准落实不等于验收通过。

暂时无法技术恢复时用 `blocked: "WO-n", reason: "原因", missing: "最小缺项"` 保持原单未通过。次数用尽和工具失败同样只写入 ops；report_text 将“待你决定”和“受阻待处理”分列，attention.md 只列真实用户问题。运维恢复经 retry/escalate 留下具体处理说明；它不增加技术预算、不跳过依赖或审阅，也不能无实际处置反复清标记重跑。

仅调整实施指令/设计引用且不改变目标、验收、权限、预算、资源、依赖和必需审阅时，负责人可用 `plan_revision` 加 `within_authorization: true`；脚本保守核对结构边界并重新绑定实施/审阅版本。语义一致性由负责人和独立审阅负责。其余实质变化仍交用户，不以该标记绕过批准。
