# 批次通道、最小设计与修订

## 默认常规通道

默认实现后由约定审阅覆盖（`E → R`），实现包含必要验证；R可覆盖多批，不要求逐批单独设置。R的repair_tasks指向所覆盖批次的修复任务；计划中的放行节点依赖覆盖它的R及其他必需门禁。技术负责人批准的局部小任务可省略设计书引用，仍保留下面的可执行要点。常规批次不配置D/DR、不建独立card.md，task.instruction直接给目标、方案要点、完成标志、允许范围/前提和验证入口，并定位设计书本批章节及对应版本，不能只引用路径而省略可执行要点。结构见[指令协议](protocol-plan.md#批次指令与设计书对应)；已有详细规格仅引用必要章节。执行者不为开工重复改写任务描述。

## 例外：需前置决定的设计通道

仅以下情况需要在实现前决定时，技术负责人配置 `D → DR → E → R`：

- 新建或改变跨模块契约，兼容、所有权或生命周期有重要未决问题。
- 涉及破坏性数据变化、不可逆操作或明确安全边界。
- 未决技术取舍会显著影响实现方向，需要先验证或决定。

技术负责人在已有instruction说明“具体未决问题、影响、为何实现后审阅来不及处理”。核心模块、并发、修改规模或不熟悉本身不是升级依据；不另写风险报告。未知事实先核查或做有界探索，探索不等于正式实现已通过。混合批次仅关键部分前置设计，其余按常规通道推进。

每项设计只记录需要先决定的内容，可写在已有规格固定章节；确无合适位置才用batches/<ID>/card.md：

```markdown
# <批次> 必要设计
- 目标与AC、范围、规格依据：引用任务和固定原文
- 关键源码事实与未决问题：依据、影响
- 契约与数据走向：只说明相关接口、所有权/生命周期和约束
- 选择及理由：解决当前问题，复用既有能力
- 验证依据：对应AC、可执行入口、必要输入与预期结果
```

不要求实施步骤流水账、完整失败路径清单、无关字段及“不适用”说明；不复制模型、预算、状态和轮次。没有当前目标依据，不引入未来扩展框架或通用抽象。设计责任由本批执行者承担，编排者只核对映射，独立审阅角色判断设计能否支撑目标。

必要设计审阅也可合并覆盖相关批次，但各成员受影响实施必须等待覆盖自己的有效设计审阅，不得为合并延后必须先决定的问题。

D与DR绑定本批design对象；E绑定design和code且依赖DR，R绑定被审实现及必要design。DR的repair_tasks指向D。仅设计通道要求有效DR的RELEASE后开始受影响实现，不能用实现后R补签。D交付VERIFIED只代表设计已交，不代表设计已审。独立首审用新上下文，同节点R2按[上下文规则](contexts.md)续接；同批D/E可续执行者自己的会话。D/DR/E/R使用计划预算，返修不清零。

## 版本及变更

常规代码变化只更新code对象。设计通道中，局部实现选择、拼写或路径更正不自动重新审设计；影响已审契约、重要约束、AC或验证依据时才更新design，重交受影响D/DR并等待有效审阅。不要把所有实现偏差都升级为设计返工；若改变任务目标或用户承诺，先上升裁决。

审阅绑定固定版本。优先引用Git固定版本或已有稳定记录；原版本会被覆盖且没有可用引用时，才保存最小必要内容，不强制逐版另建快照目录。执行者只维护一处当前设计，脚本/编排者维护引用，不同步多份卡片或报告。

任务依赖和字段见[协议](protocol.md)。通用引擎只校验已配置依赖，不自动判断技术风险或补设计节点；技术负责人负责选择通道，编排者核对本批实际门禁，不以validate成功替代配置核查。已有任务不自动删除门禁，调整需沿计划修改协议并保留历史。
