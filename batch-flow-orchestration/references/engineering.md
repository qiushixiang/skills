# 设计、实现与验证范围

技术负责人规划、执行者实施、常规和第三方审阅共同使用本规范；它定义判断范围，不新增审批节点。

## 复杂度与实现

- 方案明确目标、非目标、已有契约和验收边界。优先复用现有能力；不为未来扩展预建框架、平台或抽象。
- 抽取帮助函数须有实际复用、独立概念或隐藏复杂边界的价值；简单一次性逻辑无需拆散。复杂流程让主要路径清晰，必要细节就近命名。
- 未知输入在负责的边界验证一次；内部已由契约或类型保证的值不层层重复防御。异常处理针对实际可恢复情形，不吞错制造成功。
- 假想极端并发、安全或资源问题不能自动扩大范围。新增复杂度前说明具体可达失败、发生条件和代价；超出已有授权或承诺时取得用户决定，既有明确安全契约仍必须满足。
- 遵循目标仓库现有语言和工程规范，不把某项目的 Bun、TypeScript、导入或变量风格推广为通用门禁。

## 必要验证与证据

复用已有验证，只为验收、原缺陷反例和直接影响补必要测试；不凑类别、数量或覆盖率，不镜像实现逻辑，不新造通用测试平台。优先实际实现，外部依赖确需隔离时用最小替身，不能让模拟 PASS 代替目标行为证据。

必需验证经 `flow.py record` 运行并引用其生成记录；只读独立审阅适用[审阅流程](../workflows/review/SKILL.md)的原始工具回执例外，由宿主保存真实命令、工作目录、退出码和输出，不能将“record文件不可写”等同于“测试未执行”。执行者自述、手抄或摘录输出不能作为通过证据。命令、环境、输入、退出码与原始输出须足以复跑；检查目标确实运行，空输入、零目标、静态扫描或退出码 0 不单独证明验收。日志和报错由工具原样导出，模型只关联版本、验收结果及缺项，不改写或重排证据。已有稳定原始结果直接引用。必需验证未运行用 WAIT_EVIDENCE 或实际失败；外围允许跳过才记 SKIP/NOT_RUN 和原因，不能当通过。

## 证据记录与版本

### 足以判断本批目标的证据

- 代码：开发根、固定提交或必要工作区差异，以及实际验证的对象版本；不把基线或其他批次改动算作本批产出。
- 验证：真实命令、工作目录、影响复跑的环境/输入、退出码、相关输出及覆盖限制。优先引用稳定原生运行结果；缺关键内容时才保存最小结果。
- 结论：哪些AC已证明，哪些未运行/受阻，哪些待决定。纯设计不虚构实现验证。只针对AC、原缺陷反例和直接影响选择验证，不为材料格式重复运行。

现有引擎的evidence接口接受固定文件路径，不能直接传工具URL或Git URI。原生结果已有稳定文件时直接引用；工具记录不落盘时可用--note保存必要原文，不能用执行者自述替代实际运行输出。`record -- COMMAND`自动保存一份命令、工作目录、时间、退出码和stdout/stderr；已有充分结果时不再record。失败命令也会保存结果并返回非零，不能只看文件存在判断通过。

`--repo <仓库> --git-ref <固定引用>`自动解析为完整commit并保存仓库/提交引用，不创建Git提交，也不证明工作区与该提交一致。未提交改动可用snapshot --repo <仓库> --paths <本批范围>自动保存HEAD基线、必要diff及未跟踪文件内容，或引用已有导出结果；Git引用本身不替代差异审阅及测试。源码不在Git中时也使用相同的最小版本关联原则，不强迫建仓或提交。

脚本自动生成的必要记录放在.batch-flow/records/，无需角色命名、索引或同步。无需evidence/<任务>/<版本>/目录；原版本将被覆盖且无稳定引用时才保存最小必要副本，不复制源码树、构建树或大型产物。

### 版本与有效性

脚本内部自动计算文件哈希，角色不维护哈希。证据文件需保持固定，不能用增长中的日志、flow.json或render视图；源文件可以继续修改，历史引用不得被覆盖。Git对象需在相应仓库仍可读取；引用记录的哈希仅保护引用文件，不证明仓库对象仍存在，审阅角色仍检查实际内容。

相对evidence路径从store所在目录解析，正式记录解析为绝对路径。快捷命令的--evidence与--data.evidence遵循相同规则，推荐绝对路径。--data @file从调用工作目录读取，--repo和record --cwd也按调用工作目录解析。

源码改变时更新subject；实现交付可用finish.subject_versions关联已核实新版本，审阅结果固定在被审版本，不能自动绑定新版本。并发冲突后重新核对，不盲改revision。

已有失败、重试和历史证据不因精简而删除。临时请求若未作为证据，可在成功后不长期保留。

计时和模型来源复用原始调用及store，未知不猜；统计见[tracking.md](tracking.md)。记录数量、日志字数、测试数量和文档篇幅都不是进展指标。

`record` 不改台账，返回原命令退出码（信号或超出 1..125 时返回 1），失败也输出记录路径；`snapshot` 只读 Git HEAD 基线、指定范围 diff 及未跟踪文件，不改源码、不建提交。

## 审阅边界与问题处置

实现批次与审阅节点分别规划；相关低风险批次可合并审阅。只有关键契约需在扩散前确认、返工代价明显上升或形成独立验收边界时拆节点，不固定逐批双审，也不无限拖到最终。所有实现仍须被约定独立审阅覆盖，第三方只在计划必要节点触发。

阻断必须对应本批目标、契约或验收，给实际可达失败、影响及最小关闭条件。不能证明阻断的事项列建议，不要求执行者反证全部假想极限，不以代码风格阻断。集成批次只按约定集成目标放行，其他功能成熟度另列后续；明确的安全、性能或资源契约仍可阻断。

R2 核对原问题关闭与直接回归；发现目标内新阻断仍登记，不全量扩大范围。常规 RELEASE 不替代第三方；常规 R2 关闭第三方问题须有 can_close 权限、closes 原尝试 ID 及当前版本证据。

无阻断仍 RELEASE。技术负责人在交接边界合并决定非阻断建议为本轮修、纳入相关后续批次（必要时标最迟节点）或不采纳，收口前确认去向，不要求全部修复。只有改变计划/承诺才正式登记决定；记录非阻断 signal 时 blocks=[]。修代码后仍更新版本和必要验证，不沿用旧审阅冒充新版本通过。

以上通用原则参考 [OpenCode Style Guide](https://github.com/anomalyco/opencode/blob/dev/AGENTS.md#style-guide) 和 [Testing](https://github.com/anomalyco/opencode/blob/dev/AGENTS.md#testing)，不引入其项目专属命令。
