# batch-flow：工单驱动的分批推进

目标：用户批准计划后，大多数情况下无需人工干预，由脚本按工单派发角色（执行者、审阅者、技术负责人），角色以裁决机制互相配合，按计划目标推进到完成。用户只在四处介入：批准计划、回答问题、停止或恢复、查看汇报。

## 组成

| 部分 | 作用 |
|---|---|
| `<任务>/.batch-flow/plan.json` | 目标、交付目标、审阅组、角色模型、额度与上下文策略、环境、授权包络 |
| `orders.json` / `events.jsonl` | 工单（唯一状态）与只追加日志；只经 `bf` 脚本写入 |
| `scripts/bf/cli.py` | `init / revise / run / status / report / answer / stop / resume` |
| `scripts/start-batch-flow.sh` / `scripts/bf/front.py launch` | Claude / Codex / agy / OpenCode V2 聊天前端：后台启动和查看驱动器、每 10 分钟汇报、转交用户回答；不调度。后端能力差异见[运行与恢复](references/operations.md) |
| `scripts/agent_cli.py` | 各 CLI 后端（codex、claude、opencode、agy）的调用适配，见 [CLI 适配器](references/cli-adapter.md) |

批次设计仍保留审阅节点：计划的 `review_groups` 定义审阅范围、角色与放行批次，交付目标可依赖审阅组。运行时脚本将这些节点展开为 review、repair 等工单；工单承载执行，不替代计划中的审阅安排。

技能负责状态、角色、裁决路由、上下文与证据记录。脚本只检查协议和状态操作；修复合理性、证据充分性、版本差异影响由审阅者或技术负责人判断。具体工程方案及验证副作用边界由技术负责人在批次设计中确定，经设计审阅和授权后实施；不在技能里维护项目日志路径或产物豁免清单。

## 对外接口（项目脚本与角色可依赖）

- `bf/cli.py --base <任务>/.batch-flow record [--cwd D] -- 命令 …`：运行命令（直接子进程）并写 `records/<随机>.json`，字段 `command`(list)、`cwd`、`started_at`、`ended_at`、`exit_code`(int)、`stdout`、`stderr`；标准输出一行 `{"ok","evidence","exit_code"}`；退出码透传（0..125，否则 1）；不改工单状态。
- `bf/cli.py --base <…> snapshot --repo R --paths 文件…`：写代码快照记录，字段 `repository`、`base_commit`、`paths`、`diff`、`untracked_base64`。
- record/snapshot 按这两种结构登记并保存 SHA。引用缺失、格式异常、旧记录或非零退出码均如实交角色判断，不能据此自动判产品失败。项目的受控入口应调用 `bf record`；切换或升级技能前运行 `bf doctor` 检查任务目录是否还引用已不存在的技能脚本。

## 执行轮次

新计划使用 **cycles-v1**：每位执行者轮次可配；一轮包含一次实施交付、首次审阅，以及至多一次原作者返修和复审。复审不通过才进入下一轮或换人。返修不单独计额度，审阅预算自动配套，技术负责人协调不占实施轮次。配置、状态和旧任务边界见[执行轮次](references/execution-cycles.md)。

## 自主推进

- 用户确认仅限[六类新增用户决定](references/user-decisions.md)。技术阻塞、次数用尽和暂时无解只暂停受影响路径并报告，不自动生成 ask_user。
- 新建 cycles-v1 实施/返修采用 delivery-v2，只填“交付状态：已交付 | 未交付”。已交付直接进入独立审阅；未交付及异常协议转负责人结算裁决，只处理未完成原因、执行去向与轮次归属，不做第二次质量评审。负责人用 continue_run 指定原运行同轮继续，不另扣轮次、无正常续作次数上限；用 retry 结束原轮并按既有轮次/返修权益恢复，由驱动器选人，允许回选。原轮返修仍至多一次，拆成多次调用不增加交付机会。新轮启动即预占轮次，仅整次明确未启动可免扣。裁决/分诊不占实施轮次；裁决与审阅的非法协议修正仍有界，CLI 异常恢复独立计数。历史 intent-v1/legacy-v1 工单及在途调用保持原协议，不自动迁移或重启。
- 计划批准时一并确定已知路径权限、验证边界与预算；已批准授权的落实不重复询问用户。新增授权必须有结构化动作，关联动作整包批准和执行。
- 新版实施/返修的 CLI 异常恢复由驱动器处理：确认未启动或已结束且结果不可用时，同一轮内重试一次；连续两次异常即按原计划阶梯切换备用、负责人兜底，不先开选人裁决。新模型按本轮真实执行事实记账，历史模型的待结算占原角色额度；无下一角色才转负责人。仍在运行的调用等待，状态不明不自动重派；不按 503 等错误文案分支。裁决卡保留角色配置与共享预算供技术处置使用。
- 派发前检查明确声明的权限需求；缺项先由脚本转协调，不花实施轮次核查状态。历史登记缺陷只经带批准原文的 reconcile 修复，保留历史运行。

## 硬规则

- 独立审阅覆盖完整执行路径。cycles-v1 按每轮最多两次交付自动派生各审阅组容量，不单独配置 repair/review 额度；legacy-v1 保留原配套校验。增加执行者轮次须批准，换单和修订不重置用量。旧目标与已有审阅组不得切换计数模型；允许在原计划的新增目标上声明 cycles-v1，统一按目标解析。

- 计划已配置角色的环境声明 `require_host` 时，驱动器必须先核验自身运行环境；沙箱父进程或无法确认宿主状态时，`run`（含后台）和 `ensure-run` 在创建角色调用前失败，不消费角色额度。通过平台批准机制在既有授权宿主启动，不关闭前检或修改子 CLI 沙箱。
- 状态文件只经 `bf` 写入；不手改 plan.json、orders.json、events.jsonl。
- 计划和超出授权包络的事项（追加额度、改验收或范围）必须有用户原话文件。
- 交付协议和状态操作是否合法、下一张工单是谁，由脚本按结构判定；工程交付是否成立由审阅者/负责人判断，脚本按角色结论推进。
- 技能本身和 DONE 状态不授权提交、推送或发布；“本地提交”须是计划中明确的交付目标。

## 版本与工单传递

- 复审续用原审阅会话；负责人技术裁决与纯预算结算按同一交付目标共用会话。上述角色不应用日志大小阈值，不因新交付自动换会话。会话不可用、工具/模型变化、作者独立性冲突或显式 fresh_session 仍分别处理；实施续轮保留既有阈值。
- 快照和 SHA 只用于追溯与比较，不是修改授权或唯一归属证明。保存所有运行的版本事实，包括失败和中断；差异、采集失败、历史证据异常都送达角色，不自动否决交付或全局暂停。
- 工单及其明确引用的计划/证据提供有效要求，卡片只是导出。负责人在设计阶段选定必要背景、接口和约束，明确必读的范围与用途；各角色只收到当前有效工作及必要材料，不自动继承祖先指令、历史答复或全仓观察。原始来源和版本事实留在运行记录，派发前核对导出保真；导出错误属于工具故障，不消耗模型运行轮次。
- 计划修订不因指令/文档文字变化自动使下游失效。负责人在 plan_revision 动作的 revalidate 列出需重做的交付目标；直接 revise 可用 --revalidate D1 D2。未列出的历史结论保留，是否仍适用由角色判断。
